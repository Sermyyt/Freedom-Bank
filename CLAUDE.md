# CLAUDE.md — постоянные правила для Claude Code в этом репозитории

Проект: CQA (Conversation Quality Analytics) — кейс Freedom Broker на хакатоне.
Фронтенд (`frontend/`) — твоя зона. Бэкенд (`backend/`) пишет Codex по `AGENTS.md`.
Полное ТЗ фронта: `docs/FRONTEND_SPEC.md`. Эти правила действуют в КАЖДОЙ сессии.

## 1. Границы

- Меняй только `frontend/` и `docs/FRONTEND_NOTES.md`, `docs/FRONTEND_REQUESTS.md`.
- Не изменяй `backend/`, `AGENTS.md`, `docs/BACKEND_SPEC.md`, `docs/API_CONTRACT.md`, `docs/openapi.json`, `docs/examples/`, `.env*`, `.gitignore`.
- Если фронту не хватает чего-то в API — не обходи это и не правь бэкенд. Запиши запрос в `docs/FRONTEND_REQUESTS.md` (что нужно, зачем, какой экран блокирует) и сделай временное честное поведение в интерфейсе.
- Никогда не коммить: `data/`, `*.db`, `.env`, реальные диалоги, аудиоссылки, ссылки с `sig=`.

## 2. Источник истины об API

1. `docs/examples/*.json` — реальные ответы работающего демо-API (генерируются из кода).
2. `docs/openapi.json` и `docs/API_CONTRACT.md`.
3. `docs/FRONTEND_SPEC.md` — может содержать ошибки.

Не выдумывай поля и маршруты. Если описание расходится с примерами — верь примерам и запиши расхождение в `docs/FRONTEND_NOTES.md`.
Сервер отклоняет неизвестные поля запросов (422): отправляй только поля из контракта.

## 3. Технические правила

- Только HTML, CSS и JavaScript (ES-модули). Без фреймворков, без сборки, без npm-зависимостей, без CDN и внешних шрифтов: интерфейс должен работать офлайн и потом переноситься в HTML-компонент Dynamics 365.
- Весь интерфейс внутри одного корневого элемента `#cqa-root`, все стили под классом `.cqa-app` — без глобальных сбросов, которые ломают чужую страницу.
- Адрес API задаётся в одном месте: `frontend/js/config.js`. По умолчанию `''` (тот же origin: FastAPI раздаёт `frontend/` с `/`).
- Все запросы — только через `frontend/js/api.js`. Он снимает конверт `{data, meta}` и превращает ошибку `{error: {code, message, details, retryable}}` в объект ошибки.
- Чек-лист никогда не зашивается в код: критерии, их порядок, типы, шкалы и подписи берутся из ответа сервера. Никаких `if (criterion_id === "contact")`.
- Баллы не пересчитываются на фронте. Только форматирование до `scoring_policy.decimals` знаков.
- Текст транскрипта, обоснования, комментарии и любые строки с сервера выводятся только через `textContent` (или `createTextNode`). `innerHTML` с серверными данными запрещён.
- `audio_url` не логировать, не сохранять в `localStorage`, не показывать текстом. В `localStorage` можно хранить только настройки интерфейса (фильтры, размер страницы).
- Кроссплатформенно: человек на Windows; команды в документации — для PowerShell.

## 4. Проверки

- Чистые функции (форматирование ответов, баллов, фаз, разбор ошибок) — в `frontend/js/lib/`, тесты в `frontend/tests/*.test.mjs`, запуск `node --test frontend/tests/` (встроенный тест-раннер Node, без зависимостей).
- Каждый экран проверяй на запущенном бэкенде с `LLM_PROVIDER=fake` (команды в `docs/FRONTEND_SPEC.md`, раздел 2). Если есть браузерный инструмент — открой страницу и пройди сценарий; если нет — скажи, что визуально не проверено.
- Не объявляй сценарий рабочим, если ты его не прошёл. Пиши, что проверено и как.

## 5. Коммиты

- Маленькие коммиты по фазам из ТЗ: `frontend FN: что сделано`.
- Перед коммитом: `node --test frontend/tests/` зелёный; `git status` — нет данных, баз, `.env`; изменены только разрешённые файлы.
