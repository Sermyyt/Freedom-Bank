# Запросы фронтенда к бэкенду

Что нужно интерфейсу от API, зачем и что это блокирует. Фронтенд эти места не обходит: до решения работает честное временное поведение, описанное в каждом пункте.

## 1. Разнообразные ответы демо-провайдера (`LLM_PROVIDER=fake`)

- **Что нужно.** Детерминированно разнообразить синтетические ответы FakeLLM, сохранив пометку demo: часть бинарных критериев — «Нет», ступени шкалы ниже максимальной, N/A с `na_reason` у критерия с `na_allowed`, иногда `manual_review` с причиной, иногда флаг `true`. Для звонков с удержанием — доказательство из неклиентской фазы, чтобы сработало предупреждение о ручной проверке из контракта. Выбор может зависеть, например, от хеша ревизии и ID критерия, чтобы повторная оценка давала тот же результат.
- **Исходная проблема.** На момент запроса fake всегда ставил максимальную ступень, флаги `false`, а доказательством была первая клиентская реплика оператора. Без апелляций нельзя было показать N/A, «Нет», ручную проверку и грубое нарушение. Сценарий защиты 1:00–3:00 в ТЗ требует показать N/A.
- **Что блокирует.** Карточку разговора (F2) в сценарии защиты 1:00–3:00.
- **Прежнее временное поведение.** Интерфейс показывал эти состояния через решения апелляций: N/A с причиной, «было → стало (апелляция)», «исходно → после апелляций», плашку грубого нарушения.

- **Актуальный статус, проверка кода 2026-11-08.** Реализованы детерминированные «Нет», ступени ниже максимума, разрешённый N/A с `na_reason`, флаг «Нарушение» и ручная проверка. N/A доступен без апелляции; выбор зависит от хеша транскрипта и ID критерия. При наличии удержания/внутренней консультации fake использует неклиентское доказательство для демонстрации предупреждения. Ответы помечены demo; `checked_range` остаётся `null`. Наличие каждого состояния у конкретного разговора не гарантируется.

## 2. Политика округления в `EvaluationSummary` (низкий приоритет)

- **Что нужно.** Добавить в `EvaluationSummary` поле `scoring_policy` (или хотя бы `decimals`) — только добавление, без изменения существующих полей.
- **Исходная проблема.** Список разговоров и список оценок разговора показывали `final_total` с точностью текущего `/api/health`. Если `SCORE_DECIMALS` на сервере менялся, старые оценки в списках получали новую точность, хотя в карточке использовали свою.
- **Что блокирует.** Ничего.
- **Прежнее временное поведение.** Точность из `health.scoring_policy.decimals`.
- **Статус на 2026-11-08.** Закрыт: бэкенд передаёт сохранённую `scoring_policy` в `EvaluationSummary`; список разговоров (включая «исходно») и история оценок разговора используют её `decimals`. Если у старой сводки поле отсутствует или `null`, отображаются разряды полученного числа без подстановки текущего health и без округления до двух знаков. Обновление health не меняет показанные итоги. Проверено монтированием обеих таблиц с разными политиками и legacy-сводками.

## 3. Разговор и название критерия в `Appeal` (низкий приоритет)

- **Что нужно.** Добавить в `Appeal` поле `conversation: ConversationRef` оценки (только добавление). Желательно также добавить название критерия из снимка чек-листа.
- **Зачем.** Список `#/appeals` показывает разговор и критерий, а в `Appeal` есть только `evaluation_id` и `criterion_id`. Сейчас фронт делает по одному `GET /api/evaluations/{id}` на каждую оценку страницы, а оценка со снимком чек-листа — большой ответ.
- **Что блокирует.** Ничего; при 25 апелляциях на странице это до 25 лишних запросов.
- **Временное поведение.** Разговор и критерий подгружаются из оценки после показа строки. Если оценка не загрузилась, показаны «оценка не загружена» и ID критерия.

## 4. ID открытой апелляции в ошибке `DUPLICATE_OPEN_APPEAL` (низкий приоритет)

- **Что нужно.** Добавить в `error.details` ID уже открытой апелляции.
- **Зачем.** По ТЗ сообщение о дубле содержит ссылку на открытую апелляцию. Сейчас для этого нужен лишний `GET /api/appeals?evaluation_id=…&status=open`.
- **Что блокирует.** Ничего.
- **Временное поведение.** После 409 фронт ищет открытую апелляцию этой оценки и критерия в списке.
