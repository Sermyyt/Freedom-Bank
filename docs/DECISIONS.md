# Решения после изучения материалов — раздел 1

## D18. Применимость идентификации и проверка фактов обоснования

По повторной проверке QUALITY_NOTES и PDF чек-листа (стр. 1, 3) общий навигационный ответ без раскрытия клиентских данных и защищённого действия не требует идентификации. Seed теперь явно отделяет такую подсказку от сброса доступа, раскрытия состояния счёта и операции за клиента. Это уточнение существующего условия N/A, а не исключение для определённого разговора. Шкалы, веса и публичные поля ответов сохранены.

В cqa-v6 общее правило требует проверить роль, действие, фазу и время каждой фактической ссылки. Представление, благодарность, прощание и навигационная инструкция не доказывают другие действия только потому, что находятся рядом с нужным сообщением. Повторный прогон исправил навигационную применимость, но сохранил ложные приписывания и дал регрессии. Поэтому cqa-v7 дополнительно требует в rationale короткий дословный фрагмент именно указанного сообщения и связь с проверяемым условием; для составного условия — отдельную опору каждой части. Это способ проверить доказательство, а не новое правило начисления баллов из PDF. Для отсутствующего действия используется диапазон, для реального недостатка контекста — ручная проверка; отсутствие цитаты само по себе не означает N/A.

Критерии и ID разговоров в код не добавлены. Сохранены оба реальных прогона восьми случаев и отдельная оценка ответа и доказательств в QUALITY_NOTES. Проверка наличия строки в промпте не доказывала бы смысловое качество; даже точная цитата не гарантирует верной интерпретации. Реальные реплики и rationale не копируются в документацию, только ID и выводы. Проверенная версия чек-листа 4 сохраняет прежние шкалы и веса; исторические версии и оценки не изменяются.

## D17. Согласованность внутреннего ответа модели

Полный cqa-v3 обработал 64/65 разговоров: три попытки оставшегося разговора нарушали пару checked_range/expected_action. В cqa-v4 эта зависимость перенесена в строгую JSON Schema; реальный пробный ответ затем выявил другое нарушение — answered без ID и диапазона. В cqa-v5 схема разрешает answered с парой null/null только при хотя бы одном ID, а N/A сохраняет право не придумывать доказательства. Ветка с заполненной парой допускает отсутствие ID. Использованы поддерживаемые [Structured Outputs anyOf/minItems](https://developers.openai.com/api/docs/guides/structured-outputs); серверная валидация остаётся строгой, публичные схемы и правила человеческой апелляции не изменены.

Внутри ответа модели краткое обоснование и доказательства теперь идут перед answer: это общая попытка уменьшить наблюдавшиеся противоречия ответа собственному обоснованию. Промпт дополнен проверкой хронологии, нескольких вопросов в одной реплике, N/A и after_end. Seed уточняет сопоставление вопросов с ответами и двух частей завершения; сохранена версия 3 чек-листа. Конкретные ID разговоров в правила и код не добавлены. Эти изменения проверяются повторным прогоном; они не доказывают правильность всех смысловых оценок.

## D16. Уточнение правил без изменения шкал

Сверка cqa-v2 с PDF выявила повторяющиеся ошибки применимости, полноты ответа, порядка уточнения и завершения. В seed пояснены существующие условия needs, consultation, dialogue и closing, включая независимость грубого нарушения от других критериев. Значения вариантов, веса и допустимость N/A сохранены. Общий промпт cqa-v3 требует независимо проверять условия, все вопросы клиента и порядок действий. Создана и атомарно активирована версия 2 чек-листа; версия 1 и её оценки сохранены. Границы неоднозначностей (продолжение прежнего звонка, передача специалисту, продуктовая корректность без базы знаний) не превращены в новые жёсткие правила. Полный DEV прогон и независимая повторная сверка фиксируют фактический результат, а не предполагают устранение ошибок из-за одной правки текста.

## D15. Формат доказательств после первого настоящего запроса

Первый запрос к gpt-4.1-mini получил три ответа HTTP 200, но каждый был отклонён: модель заполняла checked_range без expected_action. Строгая проверка этой пары сохранена. В общих правилах промпта явно описаны два допустимых состояния пары и обязательное доказательство для answered без ID. Дополнительно разъяснено различие N/A и выполненного действия. PROMPT_VERSION поднят с cqa-v1 до cqa-v2; ID разговоров и критериев в логику не добавлялись. Повтор на восьми сложных разговорах принят 8/8, HTTP 429 не было; это подтверждает формат, но не семантическое качество. При сверке с PDF обнаружены ошибки применения критериев, они разбираются отдельно.

## D14. Сравнение с человеческой разметкой

Скрипт eval_gold.py измеряет original, чтобы решения апелляций не улучшали метрику модели задним числом. По умолчанию выбирается последняя реальная оценка текущей ревизии, затем проверяется версия чек-листа из разметки: при несовпадении случай исключается с VERSION_MISMATCH, без поиска более старого подходящего результата. Разметка привязана к revision_id и/или content_hash и может быть частичной; покрытие показано отдельно от точности. Невалидная метка, отсутствующий ответ и устаревшая ревизия дают явное исключение, а не неверный ответ или нулевой балл. Неоднозначные предварительные выводы ассистента не записываются как человеческий gold. API-контракт не меняется.

## D13. Пауза, указанная провайдером

При подготовке этапа настоящей модели обнаружено, что обработка Retry-After ограничивала любой запрошенный интервал восемью секундами. Это могло повторно вызвать 429 до разрешённого момента. [RFC 9110, §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3) определяет этот заголовок как время ожидания до следующего запроса; принято решение соблюдать заданный интервал полностью. Тест с MockTransport воспроизвёл 60 → 8; после исправления пауза равна 60. Ограничение экспоненциальной паузы без заголовка и числа попыток сохранено. Настройка параллелизма будет подтверждена только реальным прогоном; отсутствие 429 в автономных тестах таким подтверждением не считается.

## D12. Настоящие провайдеры и проверка качества кода

После завершения фазы 2 добавлены адаптеры OpenAI Responses и Anthropic Messages через уже установленный httpx. Схема ответа строится из выбранных критериев, полная проверка типов, N/A и доказательств остаётся на сервере. Проверены официальные [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), [Anthropic Structured Outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) и [Messages API](https://platform.claude.com/docs/en/api/http/messages/create). Имя модели задаётся конфигурацией; ключ и адрес не выводятся в ответы/ошибки. Повторы ограничены, неизвестный расход не превращается в ноль. Реальные запросы к провайдерам не выполнялись.

Пользователь дополнительно разрешил установить всё необходимое для инструментов unclebob и переработать код. После первой рабочей реализации применены ub-mode, crapper, dryer и mutator. Сложные функции делятся по ответственности при сохранении существующих поведенческих тестов; HTTP-маршруты отделены от жизненного цикла приложения и обработки ошибок. Результаты и ограничения инструментов фиксируются после фактических прогонов в WORK_LOG.

Дата: 2026-11-07. Приоритет: PDF организаторов → фактический DEV → BACKEND_SPEC.md.
Исходные AGENTS.md и BACKEND_SPEC.md сохранены без изменения содержимого (SHA-256 проверен).

## D11. Контрольная точка пройдена; первая реализация API

Пользователь принял контракт с пятью дополнениями и разрешил продолжить ТЗ. Автоматический seed/активация выполняются один раз при пустом хранилище; повторный запуск не сбрасывает выбор пользователя. `group_id` фиксирует текущие ревизии внутри транзакции постановки задания. Сохранение и активация версии атомарны и проверяют оба expected ID. Для scale отсутствующий/null normalized вычисляется сервером; при неположительном максимуме требуется явное нормирование. Решение человека допускает отсутствие доказательств с предупреждением, rationale по умолчанию равно reason.

В ТЗ фазы не пронумерованы после контрольной точки. Рабочая фаза 2 — все маршруты на fake, хранилище, полный процесс и генерация примеров; фаза 3 — настоящие адаптеры и репетиция. Следующая фаза начинается после зелёных тестов и коммита предыдущей.

Для небольшого хакатонного набора SQLite хранит документы по `(kind,id)` в одной таблице. Бизнес-операции используют `BEGIN IMMEDIATE`, включая проверки конфликтов, поэтому изменение версии/активации/апелляции атомарно. Полные снимки правил, ревизий и исходных оценок сохраняются отдельно. Единственный процесс сервера управляет ограниченным ThreadPoolExecutor; сеть и модель вызываются вне транзакций. Redis и внешняя очередь не требуются. Несколько процессов одного сервера пока не поддерживаются.

HTTP-загрузка файлов и тестовый клиент реализованы согласно [FastAPI Request Files](https://fastapi.tiangolo.com/tutorial/request-files/) и [Testing lifespan](https://fastapi.tiangolo.com/advanced/testing-events/). Дополнительно закреплены python-multipart 0.0.20 и httpx 0.28.1; реальная загрузка в тестах заменяется синтетическим ответом. Конфигурация из окружения процесса, без автоматического чтения .env. Аудиосмещение остаётся неизвестным до подтверждения соответствия записи.

## D01. Граница текущей работы

Пользователь запросил только раздел 1 и остановку на контрольной точке. Выполняются чтение источников, аудит данных, фиксация расхождений и проект API-контракта. Сейчас нет API-ответов, поэтому `docs/examples/*.json` не создаются вручную. Фронтенд не меняется.

## D02. Источники и приватные материалы

ТЗ ожидало PDF в docs/source/, но пустой проект их не содержал. Проверенные локальные PDF из Downloads/Telegram Desktop скопированы под именами из раздела 1. docs/source/, data/, .env и базы исключены из Git. Подписанная ссылка из PDF не извлекалась. Пользователь отдельно предоставил адрес для загрузки DEV; он используется только в памяти и скрытом вводе, не сохраняется в коде или конфигурации. Полный аудит с системными текстами хранится только в data/reports/; в DATA_NOTES попадают агрегаты и технические наблюдения без клиентских реплик и аудиоссылок.

## D03. Веса и отдельные флаги

ТЗ §4 требует weight > 0 при валидации, одновременно §5 определяет грубые ошибки как флаг без баллов. PDF «Чек-лист», стр. 1–2, однозначно задаёт семь балльных критериев и отдельный флаг. Решение: положительный вес только у binary/scale; у flag weight=null и normalized=null. Произвольный ID критерия не влияет на расчёт. Все флаги остаются отдельными; aggregate gross_error означает наличие хотя бы одного отмеченного нарушения.

## D04. Округление и обнуление

PDF «Чек-лист», стр. 2: округление до двух знаков; режим на ровно половине не указан. ROUND_HALF_UP из ТЗ — предварительное техническое решение, не подтверждённое правило организаторов. После контрольной точки использовать Decimal, SCORE_ROUNDING=half_up и SCORE_DECIMALS=2, закрепляя политику в оценке. Изменение конфигурации не должно менять результат старой апелляции. Грубые ошибки PDF требует отмечать отдельно; автоматическое обнуление не предписано. GROSS_ERROR_ZEROES_TOTAL=false по умолчанию. Вопрос режима округления остаётся менторам.

## D05. Точные формулировки и звонки

Основные веса, ступени и условия N/A в §5 совпадают с PDF. Сокращённые пересказы описаний шкал в ТЗ не следует копировать в seed вместо полных формулировок PDF. У завершения сохраняется формулировка «подвёл итог или предложил дальнейшую помощь и попрощался»; логическая группировка требует уточнения ментора. Гайд требует обработку звонков, но чек-лист описывает чаты: правила адаптации и различение нескольких сотрудников с общей ролью operator не уточнены. Семантические ожидания из §11 — гипотезы до проверки, а не эталонные метки.

## D06. Время транскрипта и аудио

ТЗ §8.4 называет случаи ненадёжности смещения, но не даёт доказательства надёжности в остальных случаях. По гайду время звонков — ISO с часовым поясом. Разность времён реплик сама по себе не устанавливает начало записи или длительность пауз. Контракт различает offset_sec и audio_offset_sec; второе null до положительной проверки соответствия записи. Наличие пауз гарантированно снимает audio_offset_reliable. Исходные метки и тексты остаются неизменными.

## D07. Неполная оценка и ручная проверка

§6 говорит о статусе ручной проверки при невалидном ответе, §7 допускает явную ошибку или ручную проверку. Контракт: при отсутствии валидного применимого ответа итог null; задача не выдаёт такой результат за успешную оценку. Валидный, но неоднозначный ответ может быть manual_review с итогом. Ошибка одного элемента пакета не уничтожает результаты других. Это проект поведения, реализация после контрольной точки.

## D08. Договорённости API

Все операции под /api; отдельные UUID для логического разговора и неизменяемой ревизии. Внешние group_id/conversation_id сохраняются. Оценка запускается по явным revision_ids и фиксирует версию чек-листа. Версия активации глобально одна; старые задачи не меняются. Ответы имеют data/meta, ошибки error/meta. Баллы передаются JSON-числами; сервер считает Decimal, фронтенд только форматирует.

Апелляция сохраняет original; confirm подтверждает текущий final. После ранее разрешённой апелляции возможна новая, поэтому проверяется expected_final_revision. Решение и пересчёт атомарны. Секции имеют отдельные completion_percent и contribution. Контракт добавляет защиту от конкурентного изменения активной версии и последней версии чек-листа. Предыдущего контракта в проекте не было; BREAKING-изменений нет.

## D09. Аудит данных не является импортом

data_report.py не изменяет исходный JSON и не реализует хранилище. Полная диагностическая статистика учитывает даже пустые транскрипты и повторные ID, чтобы обнаружить их; боевой импорт по контракту сможет их отклонить с отчётом. record_index в локальном аудите начинается с 1; индекс ошибки JSON/multipart API начинается с 0. ID сообщения в обоих случаях начинается с 1. --group выбирает уже загруженный локальный JSON, сетевой импорт появится после контрольной точки. Известные фразы взяты из §8.1 как проверяемый словарь данных; неизвестные не угадываются.
