# Задание для Claude Code: фронтенд Conversation Quality Analytics (Freedom Broker)

Сделай рабочее место проверяющего качества: веб-интерфейс к уже работающему бэкенду CQA. Проверяющий импортирует разговоры операторов с клиентами (чаты и звонки, RU/KZ/EN), запускает оценку по чек-листу, видит баллы с доказательствами, рассматривает апелляции и меняет чек-лист без изменения кода.

Команда — два человека, хакатон 24 часа. Бэкенд готов на демо-провайдере (`LLM_PROVIDER=fake`, оценки синтетические). Постоянные правила — в `CLAUDE.md`, они обязательны во всех сессиях.

---

## 1. Что будут проверять судьи

**Защита, 5 минут** — интерфейс должен пройти это без единой правки кода:

| Время | Что показываем |
|---|---|
| 0:00–1:00 | Список разговоров, открываем один диалог, интерфейс |
| 1:00–3:00 | Оценка: баллы по критериям, переход к доказательству в переписке, N/A, итог |
| 3:00–4:00 | Апелляция: оператор оспаривает критерий, проверяющий решает, итог пересчитан, история сохранена |
| 4:00–5:00 | Замена критерия через редактор, новая версия чек-листа применяется к оценке |

**Контрольный набор на 23-м часу.** Организаторы дают новый `group_id`. В интерфейсе: импорт группы → «Оценить всю группу» → прогресс → результаты в списке. Без правок кода.

**Наше отличие** — фазы разговора. В звонках оператор ставит клиента на удержание и советуется с коллегой; клиент этих реплик не слышит. Интерфейс должен это явно показывать (раздел 5.1), а судья должен увидеть, что такие реплики не засчитаны как общение с клиентом.

Требование организаторов: интерфейс на HTML, CSS и JavaScript со структурой, пригодной для переноса в HTML-компонент Dynamics 365. Интеграция с Dynamics, авторизация и распознавание речи не нужны.

## 2. Сначала изучи и запусти

1. Прочитай `CLAUDE.md`, этот файл, `docs/API_CONTRACT.md` и все `docs/examples/*.json`. Примеры — реальные ответы сервера; формы данных бери из них.
2. Запусти бэкенд (PowerShell, из корня репозитория). **Папка `frontend/` должна существовать до запуска сервера** — иначе он не начнёт раздавать её с `/`; после её создания перезапусти сервер.
   ```powershell
   python -m venv .venv
   .\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
   Set-Location backend
   $env:LLM_PROVIDER = 'fake'
   ..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
   ```
   Проверь `http://127.0.0.1:8000/api/health` и Swagger `http://127.0.0.1:8000/docs`. Интерфейс будет открываться на `http://127.0.0.1:8000/`.
3. Данные для разработки: если у человека есть локальный `data/raw/DEV.json`, импортируй его через собственный экран импорта файла (раздел 5.2) — это заодно проверит импорт. Реальные диалоги не копируй в `frontend/` и в тесты; для тестов используй синтетику по образцу `docs/examples/`.
4. Запиши в `docs/FRONTEND_NOTES.md`: как запускать, что заметил в API, какие решения принял.

## 3. Структура

```
frontend/
  index.html              одна страница, <div id="cqa-root" class="cqa-app">
  css/styles.css          все правила под .cqa-app
  js/config.js            export const API_BASE = ''   (для Live Server: 'http://127.0.0.1:8000')
  js/api.js               fetch-обёртка, конверты, ошибки, multipart
  js/router.js            hash-маршруты
  js/state.js             health, активная версия, текущие фильтры
  js/views/conversations.js   список + импорт + оценка группы
  js/views/conversation.js    карточка разговора + оценка
  js/views/checklist.js       редактор чек-листа
  js/views/appeals.js         список и решение апелляций
  js/views/compare.js         сравнение двух оценок
  js/views/history.js         история
  js/components/          toast, modal, badge, progress, empty-state
  js/lib/                 чистые функции (format, answers, phases, errors, poll)
  tests/*.test.mjs        node --test
```

Маршруты (hash, без сервера маршрутизации):
- `#/conversations` — список (по умолчанию)
- `#/conversation/<id>?revision=<revision_id>&evaluation=<evaluation_id>` — карточка; параметры необязательны
- `#/checklist` — редактор
- `#/appeals` — апелляции
- `#/compare?left=<evaluation_id>&right=<evaluation_id>`
- `#/history`

### 3.1 `api.js`

- Базовый адрес из `config.js`, все пути под `/api`.
- Успех: вернуть `body.data`. Ошибка HTTP: бросить `ApiError { status, code, message, details, retryable, requestId }` из `body.error` и `body.meta.request_id`. Если тело не JSON — `code: "NETWORK_OR_SERVER"` и общее русское сообщение.
- `error.message` уже безопасный русский текст — его и показывай. `details[].path` используй, чтобы подсветить поле формы.
- 429 `BUSY`: показать «Сервер занят, повторите через N с» по заголовку `Retry-After`. POST автоматически не повторять никогда.
- Загрузка файла — `FormData` с полем `file` и необязательным `group_id`; заголовок `Content-Type` не задавать вручную.

### 3.2 Опрос заданий (`lib/poll.js`)

`POST /api/evaluations` возвращает задание (202). Опрашивай `GET /api/jobs/{id}` раз в секунду до `completed` или `failed`. Останавливай опрос при уходе с экрана. Показывай `processed/total`, `succeeded`, `failed`, `manual_review_count` и ошибки элементов из `items[].error.message`. Статус `failed` у задания при части успешных элементов — это «готово с ошибками», успешные результаты показывай.

## 4. Общие элементы

- **Шапка:** название, вкладки (Разговоры, Чек-лист, Апелляции, История), активная версия чек-листа («Чек-лист v3»), состояние сервера из `/api/health`.
- **Отметка демо:** при `is_demo=true` (в health, оценке или задании) — постоянная заметная плашка «Демо: оценки синтетические». Не прятать.
- **Ответы** (`lib/answers.js`, по типу критерия из снимка чек-листа):
  - `binary`: `true` → «Да», `false` → «Нет»;
  - `scale`: подпись `label` ступени с таким `value`;
  - `flag`: `true` → «Нарушение», `false` → «Нет нарушения»;
  - `status: "not_applicable"` → «N/A»; `status: "invalid"` → «Нет валидного ответа».
  - Сравнение строгое: `true` не равно `1`.
- **Числа:** итог и баллы приходят готовыми — только форматирование `Intl.NumberFormat('ru-RU')` с `scoring_policy.decimals` знаками. `null` итог → «—» и рядом `total_reason`.
- **Фазы** (`lib/phases.js`): `pre_operator` «До оператора», `client` — без пометки, `hold` «Удержание», `internal_consult` «Внутренняя консультация», `after_end` «После завершения». Неизвестное значение — показать как есть, не падать.
- **Системные события:** человекочитаемые подписи для кодов из контракта (`escalation`, `identity_verified`, `hold_start`, …), неизвестный код — как есть.
- **Ошибки:** всплывающее сообщение с `message`; в формах — у поля по `details.path`. Без технических трассировок.
- **Пустые состояния** у каждого списка: что сделать дальше («Импортируйте набор…»).
- Внешний вид — спокойный, рабочий, читаемый. Без логотипов и фирменного стиля Freedom. Цвет не единственный носитель смысла: у статусов есть текст.

## 5. Экраны (в порядке приоритета)

### 5.1 Карточка разговора — главный экран защиты

Загрузка: `GET /api/conversations/{id}` (с `revision_id`, если пришёл в адресе). Оценки этого разговора: `GET /api/evaluations?conversation_id=<ref.id>` (сначала новые); открыть выбранную или последнюю через `GET /api/evaluations/{id}`.
Если `evaluation.conversation.revision_id` отличается от показанной ревизии — загрузи именно ту ревизию: доказательства относятся к ней.

**Слева — переписка:**
- Каждое сообщение: номер `#id`, роль (клиент / оператор / бот / система), время `timestamp`, текст.
- Системные события — компактной строкой с подписью события.
- Подряд идущие сообщения в фазах `hold` / `internal_consult` объединены в блок с боковой полосой и подписью «Клиент на удержании — не слышит» / «Внутренняя консультация — клиент не слышит». Сообщения с `client_facing=false` визуально приглушены.
- Флаги: `duplicate_of_prev` → «дубль #N» (`duplicate_of_message_id`), `after_end` → «после завершения», `pii_masked` → «данные скрыты», `unknown_event` → «неизвестное событие».
- Звонок: если `audio_url` есть — `<audio controls preload="none">` над перепиской. Если `audio_offset_reliable=false` — подпись «Точное время в записи не гарантировано». Кнопку перехода по времени показывать только при `audio_offset_sec != null`.

**Справа — оценка:**
- Кнопка **«Оценить»**: `POST /api/evaluations` с `{"revision_ids": [ref.revision_id]}` → опрос задания → открыть `items[0].evaluation_id`. Кнопка недоступна, пока идёт задание; при `evaluation_ready=false` в health — подсказка из ошибки сервера.
- **Итог:** `final.total` крупно. Если `original.total` отличается — «исходно X → после апелляций Y». Статус `manual_review` — плашка «Нужна ручная проверка» с `manual_review_reasons`. `gross_error=true` — отдельная красная плашка «Грубое нарушение» (не смешивать с баллом).
- **Секции:** название, `completion_percent` подписан «выполнение секции», `contribution` — «вклад в итог». Это разные числа, подписи обязательны.
- **Критерии** в порядке `checklist_snapshot.criteria`. Для каждого:
  - название, ответ (раздел 4), `weighted_points` из `original_weight`, эффективный вес;
  - `rationale`;
  - доказательства: кнопки `#12` из `evidence` — по клику переписка прокручивается к сообщению и подсвечивает его; у доказательства из неклиентской фазы — пометка фазы;
  - `checked_range` — подсветка диапазона сообщений и текст «Ожидалось: `expected_action`»;
  - `na_reason` для N/A; `warnings`; `manual_review_reasons`; пометка «переиспользовано из прошлой оценки» при `reused=true`;
  - если в `final` ответ отличается от `original` — «было: Нет → стало: Да (апелляция)»;
  - кнопка **«Оспорить»** (раздел 5.3).
- Флаги (тип `flag`) показываются отдельным блоком под критериями.
- Список прошлых оценок разговора (дата, версия чек-листа, итог) с выбором и кнопкой «Сравнить с текущей» → `#/compare`.

### 5.2 Список разговоров

- **Импорт:**
  - по группе: поле `group_id` → `POST /api/imports/dataset` `{"group_id": "..."}`. При `dataset_ready=false` в health — кнопка недоступна с подсказкой «На сервере не настроен DATASET_URL; используйте загрузку файла»;
  - файлом: выбор `.json` → `POST /api/imports/file` (multipart `file`, поле `group_id` — для голого массива обязательно, для полного ответа организаторов необязательно).
  - После импорта показать отчёт: получено / новых / без изменений / изменённых / пропущено, ошибки и предупреждения списком, число нераспознанных системных фраз (сами фразы — по раскрытию). Затем обновить список с фильтром по этой группе.
- **Фильтры:** группа, язык, канал, статус оценки, грубое нарушение, открытые апелляции, поиск по внешнему ID (`q`). Пагинация `limit`/`offset` (25/50/100). Фильтры хранить в адресе или `localStorage`.
- **Таблица:** внешний ID, группа, канал (чат/звонок), язык, сообщений, итог (`latest_evaluation.final_total`), статус, грубое нарушение, открытые апелляции, отметка демо. Клик по строке → карточка.
- **«Оценить всю группу»:** `POST /api/evaluations` с `{"group_id": "..."}` (без `revision_ids`) → полоса прогресса задания → по окончании обновить таблицу. Это главный сценарий 23-го часа.

### 5.3 Апелляции

**Подача** (из карточки, кнопка «Оспорить»): модальное окно с текущим ответом критерия и полем комментария → `POST /api/appeals` `{"evaluation_id", "criterion_id", "comment"}`. 409 `DUPLICATE_OPEN_APPEAL` → «По этому критерию уже есть открытая апелляция» и ссылка на неё.

**Список** `#/appeals`: `GET /api/appeals` с фильтром статуса (открытые по умолчанию): разговор, критерий, комментарий, дата, статус.

**Решение** (из списка или из карточки) — `POST /api/appeals/{id}/decision`, ответ `{appeal, evaluation}`:
- Перед решением заново загрузить оценку (`GET /api/evaluations/{id}`) и взять `final_revision` как `expected_final_revision`.
- Показать текущий финальный ответ критерия, обоснование и доказательства.
- «Подтвердить» → `{"action": "confirm", "reason", "expected_final_revision"}`.
- «Изменить» → выбор нового ответа строится из опций критерия в `checklist_snapshot` этой оценки (+ «N/A», только если `na_allowed`; тогда обязательно `na_reason`), обязательная причина, необязательно — доказательства (клик по сообщениям в переписке добавляет `#id`). Отправлять `new_answer: {"status": "answered", "value": ...}` или `{"status": "not_applicable", "value": null}`.
- После ответа показать пересчёт: итог до → после, и обновить карточку.
- 409 `VERSION_CONFLICT` → «Оценка изменилась, данные обновлены» + перезагрузка. 409 `APPEAL_ALREADY_RESOLVED` → обновить список.
- Подача и решение — два отдельных действия в интерфейсе (так требует ТЗ).

### 5.4 Редактор чек-листа

- Загрузить активную версию: `active_checklist_version_id` из health → `GET /api/checklist-versions/{id}`; список версий — `GET /api/checklists/{checklist_id}/versions`.
- Редактирование: название и описание чек-листа; критерии — добавить, удалить, переместить вверх/вниз. Поля критерия: `id` (у существующих только для чтения; у нового — ввод латиницей, подсказка «новый ID для нового правила»), `name`, `description`, `section`, `answer_type` (`binary` / `scale` / `flag`), `weight` (скрыт у `flag`), `na_allowed` и `na_condition`.
- Опции: у `binary` и `flag` — ровно `true`/`false` с подписями и описаниями; у `scale` — ступени (значение, подпись, описание, `normalized` необязательно, с подсказкой «авто: значение / максимум»).
- Живая проверка: через 500 мс после изменения — `POST /api/checklists/validate`; ошибки показывать у полей по `details.path`, предупреждения — отдельно.
- Сохранение: `POST /api/checklists/{checklist_id}/versions` с полями определения + `expected_latest_version_id` + `activate` (галочка «Сразу применить», включена по умолчанию) + `expected_active_version_id` из свежего health (в том числе `null`). 409 `VERSION_CONFLICT` → «Чек-лист изменился, загружена последняя версия».
- После сохранения с активацией — предложить «Переоценить этот разговор» (вернуться в карточку и нажать «Оценить») и затем «Сравнить с прошлой оценкой».

### 5.5 Сравнение

`GET /api/evaluations/compare?left_id=...&right_id=...`. Таблица по `criteria`: критерий, тип изменения (`added` «добавлен», `removed` «удалён», `definition_changed` «правило изменено», `weight_changed` «изменён вес», `unchanged`), ответ слева и справа, `contribution_delta`. Сверху — итоги и `total_delta`. `null`-разница — «—», а не 0. Это объясняет судье, как замена критерия изменила балл.

### 5.6 История

`GET /api/history` с фильтрами (разговор, оценка, апелляция, тип события): время, событие, краткое описание, ссылки на связанные объекты. Низший приоритет.

## 6. Фазы работы

Каждая фаза заканчивается зелёным `node --test frontend/tests/`, проверкой на запущенном бэкенде и коммитом.

| Фаза | Содержание | Готово, когда |
|---|---|---|
| F0 | Изучение, запуск бэкенда, `FRONTEND_NOTES.md` | health открывается, примеры прочитаны |
| F1 | `api.js`, роутер, шапка, плашка демо, список, импорт файла и группы | файл импортируется, список с фильтрами работает |
| F2 | Карточка: переписка, фазы, флаги, аудио, «Оценить», опрос, баллы, доказательства с переходом | демо 0:00–3:00 проходит |
| F3 | Апелляции: подача, список, решение, пересчёт, конфликты | демо 3:00–4:00 проходит |
| F4 | Редактор, проверка, сохранение с активацией, переоценка, сравнение | демо 4:00–5:00 проходит |
| F5 | «Оценить всю группу» с прогрессом, история, пустые состояния, полировка | сценарий 23-го часа проходит |
| F6 | Репетиция: весь сценарий защиты и 23-го часа по шагам; записать в `FRONTEND_NOTES.md`, что проверено | человек может провести защиту по записи |

Приоритет при нехватке времени: F2 → F3 → F4 → F1-импорт → F5 → история и полировка.

## 7. Тесты (минимум, `node --test`)

- `api.js`: успешный конверт → `data`; ошибка → `ApiError` с `code`, `message`, `details`; не-JSON ответ → общая ошибка (`fetch` подменяется в тесте).
- Ответы: `binary` true/false, `scale` → подпись ступени, `flag`, N/A, invalid, строгое `true !== 1`.
- Числа: форматирование с 0 и 2 знаками, `null` → «—».
- Фазы: группировка подряд идущих `hold`/`internal_consult` в блоки, неизвестная фаза не ломает.
- Апелляция: из опций критерия и выбора человека собирается ровно тело запроса из контракта (без лишних полей).
- Опрос: останавливается на `completed` и `failed`, не повторяет POST.

## 8. Чего не делать

- Не менять бэкенд и контракт; не добавлять поля, которых нет в контракте.
- Не зашивать восемь исходных критериев, их ID или названия.
- Не пересчитывать баллы и не округлять их по-своему.
- Не использовать `innerHTML` с данными сервера.
- Не подключать фреймворки, сборщики, CDN, внешние шрифты.
- Не сохранять транскрипты и аудиоссылки в браузере.
- Не показывать демо-оценки как настоящие.

В финале сообщи: что реализовано, как запустить, какие сценарии пройдены и как это проверено, что не проверено, какие запросы к бэкенду записаны в `docs/FRONTEND_REQUESTS.md`.
