Разработай рабочий бэкенд проекта Conversation Quality Analytics для хакатона Freedom Broker.

Реализуй полный процесс:

## 3. Импорт и хранение данных

Подписанную ссылку организаторов человек сам кладёт в `.env` (`DATASET_URL`). Не извлекай её из PDF и не пиши её в код, документацию, тесты, логи и примеры. Запрос к организаторам выполняй с сервера: `group_id` подставляется параметром запроса, остальные параметры ссылки сохраняются.

Формат ответа:

```json
{
  "error": "",
  "isSuccess": true,
  "data": {
    "dataset_group_id": "DEV",
    "total_records": 65,
    "records": [{
      "conversation_id": "p1-ru-001",
      "channel": "agent chat",
      "language": "RU",
      "transcript": [{
        "timestamp": "00:02",
        "speaker": "operator",
        "text": "Здравствуйте!"
      }],
      "audio_url": null
    }]
  }
}
```

Проверяй `isSuccess` и общую структуру ответа. Также предусмотрен импорт JSON без обращения к организаторам (загрузка файла; принимай и полный ответ, и голый список `records`).

**Импорт должен быть терпимым к неизвестному**, иначе контрольный набор может упасть на 23-м часу:
- известные значения — роли `client`, `operator`, `bot`, `system`; каналы `agent chat`, `voice call`; языки `RU`, `KZ`, `EN`;
- неизвестная роль, канал или язык → сохраняется как есть, в отчёт импорта идёт предупреждение; запись не отклоняется;
- запись без обязательных полей или с битой структурой пропускается с ошибкой в отчёте, остальные записи импортируются;
- отчёт импорта: получено / новых / без изменений / изменённых / пропущено / ошибки / предупреждения / нераспознанные системные фразы.

Сохраняй исходный текст, порядок сообщений, роли и исходные временные метки:
- чаты: `MM:SS` от начала (поддержи и `H:MM:SS`);
- звонки: ISO 8601 с часовым поясом.

Дополнительно вычисляй `offset_sec` — секунды от начала разговора (для звонков — от первого сообщения). Если метка не разобралась — `null`, а не ошибка.

ID сообщения — его номер в разговоре, начиная с 1 (так люди называют «сообщение №12»). Уникальность — в пределах группы и разговора. Повторный импорт того же содержимого не создаёт дубликатов. Изменённый транскрипт сохраняется как новая ревизия разговора; уже сохранённые оценки продолжают ссылаться на свою ревизию и не подменяются незаметно.

Учитывай принадлежность разговора к набору: одинаковые внешние `conversation_id` в разных группах не должны конфликтовать.

Храни разговоры, версии чек-листов, оценки, задания обработки, апелляции и историю решений в базе. Данные должны сохраняться после перезапуска.

## 4. Динамические чек-листы

Критерий содержит:
- устойчивый ID;
- название и описание правила;
- секцию;
- тип ответа;
- вес для оцениваемых критериев;
- допустимые значения или ступени шкалы с описаниями;
- разрешение N/A и условие неприменимости;
- нормированное значение для каждого ответа.

Поддержи бинарный ответ, дискретную числовую шкалу и отдельный флаг нарушения без баллов.

Нормирование задавай явно, без формульного языка: у каждой ступени шкалы есть поле `normalized` (число от 0 до 1). Для бинарного ответа Да = 1, Нет = 0. Для исходных шкал `normalized = value / max_value`. Для новой шкалы, созданной в интерфейсе, `normalized` каждой ступени обязателен; API может подставлять `value / max_value` как значение по умолчанию, но в версии чек-листа оно хранится явно.

Количество и ID критериев произвольные. Исходные восемь критериев — начальная конфигурация (seed JSON). Добавление, удаление или замена критерия не должны требовать изменения серверного кода или статической схемы промпта: и промпт, и JSON-схема ответа модели собираются из текущей версии чек-листа.

Проверяй конфигурацию: уникальность ID, вес > 0, непустые шкалы без повторов, `normalized` в [0, 1], условие N/A задано, если N/A разрешён. Отдельный эндпоинт проверки без сохранения поможет редактору на фронте.

Каждое изменение создаёт новую версию. Оценка хранит ссылку на неизменяемую версию и снимок применённых правил. Смена чек-листа не переписывает старые результаты.

Секции — простые: строковое поле `section` у критерия. Приоритет у секций низкий (см. приоритеты в разделе 15).

## 5. Исходный чек-лист

Перенеси формулировки и шкалы из PDF без потери условий:

1) **Установление контакта.** Да/Нет, вес 10, N/A запрещён.
Оператор поздоровался на языке клиента и представился в первом ответе.

2) **Выявление потребности.** Да/Нет/N/A, вес 15.
Оператор учёл известные детали и уточнил недостающее до ответа.
N/A — данных для ответа хватало с самого начала.

3) **Идентификация.** Да/Нет/N/A, вес 20.
Проверка личности подтверждена до раскрытия данных или защищённого действия.
N/A — запрос не требовал идентификации.
Если проверка требовалась, но не подтверждена, ответ — Нет.

4) **Корректная и полная консультация.** Шкала 0, 5, 10, 15, 20; вес 20; N/A разрешён.
20 — существенные вопросы закрыты или дан корректный следующий шаг.
15 — основной вопрос решён, пропущена второстепенная деталь.
10 — существенная часть запроса осталась открытой.
5 — общая подсказка без понятного дальнейшего действия.
0 — ответа по существу нет или ключевая рекомендация ошибочна.
N/A — разговор закончился до формулировки запроса клиентом.

5) **Эмпатия и клиентоориентированность.** Да/Нет, вес 15, N/A запрещён.
Вежливость и реакция на конкретную проблему, если клиент выразил недовольство или описал неудобство.

6) **Управление диалогом, скорость и грамотность.** Шкала 0, 4, 7, 10; вес 15; N/A запрещён.
10 — ясно и связно, при явном ожидании оператор предупредил.
7 — один заметный сбой, но ответ понятен.
4 — клиент переспрашивает из-за формулировок или порядка ответов.
0 — бессвязность или противоречия мешают понять разговор.

7) **Завершение.** Да/Нет/N/A, вес 5.
Сохрани формулировку организаторов: «оператор подвёл итог или предложил дальнейшую помощь и попрощался».
N/A — разговор оборвался до возможности его завершить.
Неоднозначности трактовки зафиксируй в документации.

8) **Грубые ошибки.** Да/Нет, без баллов.
Да — оскорбление клиента, предложение платной услуги в обход компании или раскрытие конфиденциальной информации.
Предложения личного инвестирования или частной платной консультации достаточно: согласие клиента не требуется.

Порог первой реакции в три минуты, теги и вложения в оценку не входят.

Правила, относящиеся к конкретному критерию, храни в его описании (данные), а не в коде промпта.

## 6. Расчёт баллов

Выполняй расчёт обычным кодом (`backend/app/scoring.py`), независимо от арифметики модели.

Для применимых критериев с положительным весом:

```
total = round(
  100 * sum(weight_i * normalized_answer_i)
      / sum(applicable_weight_i),
  2
)
```

- N/A исключается из числителя и знаменателя.
- Промежуточные вычисления не округляй.
- **Не используй встроенный `round()` и float для итога:** в Python это банковское округление (63.125 → 63.12). Считай в `Decimal`, округляй `ROUND_HALF_UP`. Режим и число знаков — в конфиге (`SCORE_ROUNDING=half_up`, `SCORE_DECIMALS=2`): правило округления ещё уточняется у менторов.
- Если применимых критериев с положительным весом нет, `total = null` с понятным объяснением.
- Если у применимого критерия нет валидного ответа (ошибка модели после повторов), `total = null`, статус оценки — ручная проверка. Не считай итог по неполным данным.
- Грубое нарушение сохраняется отдельным флагом и по умолчанию не обнуляет итог. Поведение — в конфиге (`GROSS_ERROR_ZEROES_TOTAL=false`); при `true` сохраняй и итог до обнуления.

Возвращай исходные веса, нормированные ответы, эффективные веса после N/A и вклад каждого критерия.

Поддержи результаты секций. Явно различай процент выполнения секции и её вклад в общий результат. Способ отображения секционных результатов опиши в `API_CONTRACT.md`.

## 7. Оценка моделью

Сделай отдельный адаптер провайдера модели (`openai`, `anthropic`, `fake`). Модель, ключ, адрес API и тайм-ауты задаются конфигурацией; имя модели в коде не хардкодь. Перед подключением проверь официальную документацию выбранного провайдера (если сети нет — используй установленную версию SDK и запиши это в `DECISIONS.md`). Если строгий режим JSON-схемы провайдера не поддерживает нужную конструкцию — упрости схему для модели, а полную проверку оставь в Pydantic.

Оценщик получает полный разговор и текущую версию чек-листа. Каждое сообщение передаётся строкой с ID, ролью, фазой, признаком «часть общения с клиентом», кодом системного события и флагами (дубль, после завершения). Транскрипт передаётся как отделённый блок данных.

Обоснования пиши на русском (конфиг `RATIONALE_LANGUAGE=ru`) независимо от языка диалога, со ссылками вида `#12`.

Структурированный результат по критерию содержит:
- `criterion_id`;
- ответ или числовую оценку либо N/A;
- короткое объяснение;
- ID сообщений-доказательств;
- проверенный диапазон сообщений для пропущенного действия;
- причину N/A, когда оно применено;
- признак необходимости ручной проверки и объяснение, если есть неоднозначность.

Проверяй:
- присутствуют ровно ожидаемые ID критериев;
- отсутствуют повторяющиеся и неизвестные ID;
- ответы соответствуют типам и разрешённым ступеням;
- N/A разрешён настройкой;
- доказательства существуют;
- диапазоны корректны;
- если все доказательства положительного ответа — реплики вне общения с клиентом (удержание, внутренняя консультация, после завершения), ставь предупреждение и ручную проверку.

Цитаты формируй из сохранённых сообщений по ID. Не доверяй сгенерированному тексту цитаты как источнику.

Для отсутствующего действия требуй участок проверки и описание того, какое действие ожидалось. Неуверенность модели не превращай в N/A.

Текст диалога не может переопределять инструкции оценщика. Добавь проверку на попытку клиента в переписке приказать системе поставить высокий балл.

При ошибке схемы допускаются ограниченные повторные попытки (передай модели список ошибок). После исчерпания возвращай явную ошибку или статус ручной проверки, не имитируй успешную оценку.

Если API-ключ отсутствует, сохрани работоспособность импорта, конфигураций и остальных функций. Реальный запуск оценки должен сообщать об отсутствии настройки. Поддельный провайдер допустим для тестов и явно обозначенного демонстрационного режима; его результаты в API помечены как демо.

Сохраняй модель, версию промпта, длительность, число вызовов и расход токенов, если провайдер его сообщает. Сохраняй и сырой ответ модели — он нужен при разборе апелляций. Стоимость учитывает все вызовы и повторы. Если тариф или расход неизвестен, стоимость должна быть неизвестной, а не нулевой.

### Переиспользование и частичная переоценка

Это важно для живой проверки «замена критерия»: пересчёт должен занимать секунды, а остальные критерии не должны меняться случайно.

- Результат критерия кешируется по ключу: ревизия транскрипта + хеш определения критерия (всё, кроме веса и порядка) + флаги разговора, влияющие на оценку + модель + версия промпта + настройки оценщика.
- Замена или добавление одного критерия → модель вызывается только для изменённых и новых критериев, остальные результаты переиспользуются (в ответе помечены как переиспользованные).
- Изменение только веса → пересчёт баллов без вызова модели.
- Новый критерий никогда не получает результат старого критерия.
- Параметр `force` отключает переиспользование.

## 8. Контекст разговора и фазы

Оценивай действия оператора:
- приветствие бота не засчитывается оператору;
- сведения клиента до подключения оператора учитываются;
- системное подтверждение идентификации может быть доказательством;
- идентификация должна предшествовать защищённому действию;
- корректная передача специалистам может быть правильным следующим шагом.

Нормализация перед сравнением: обрезать пробелы, нижний регистр, схлопнуть пробелы, убрать конечную точку. События завершения: `client_ended`, `operator_closed`, `client_left`, `connection_lost`.

### 8.2 Фазы

Каждому сообщению присваивай фазу и признак `client_facing` (часть общения с клиентом). Реализуй как общее поведение по событиям, без привязки к конкретным ID разговоров.

Фазы: `pre_operator`, `client`, `hold`, `internal_consult`, `after_end`.

Правила (проход по сообщениям по порядку):
1. `pre_operator` — до первого сообщения с ролью `operator` (бот, клиент до подключения, системные события).
2. `hold_start` включает удержание; `hold_end` выключает. **Всё строго между ними — не общение с клиентом**, независимо от событий консультации. Само сообщение `hold_start` — уже `hold`, само `hold_end` — уже `client`.
3. Внутри удержания: после `consult_started` — `internal_consult`; после `agent_left` — снова `hold` (оператор всё ещё не с клиентом).
4. `consult_initiated` вне удержания фазу не меняет: клиент ещё на линии.
5. После события завершения все следующие сообщения — `after_end` (само событие — в текущей фазе).
6. `client_facing = true` для `pre_operator` и `client`, иначе `false`.
7. Удержание без `hold_end` длится до конца разговора; добавь причину ручной проверки.
8. Опционально: номер сегмента, увеличивается после `transfer_to_support`. Не выдумывай идентификаторы сотрудников, которых нет в данных.

Ожидаемый результат на DEV `p4-ru-002` (проверено на данных; тест на реальных данных — с `skipif`, если файла нет; для публичных тестов сделай синтетическую фикстуру с той же последовательностью событий):

| Сообщения | Фаза | client_facing |
|---|---|---|
| 1–2 | `pre_operator` | true |
| 3–17 | `client` (16 — `consult_initiated`, 17 — клиент «Хорошо.») | true |
| 18 | `hold` (`hold_start`) | false |
| 19–46 | `internal_consult` (19 — `consult_started`) | false |
| 47–58 | `hold` (47 — `agent_left`, дальше оператор говорит не с клиентом) | false |
| 59–72 | `client` (59 — `hold_end`, 72 — `client_ended`) | true |

Внутренне обсуждённое объяснение нельзя автоматически считать сообщённым клиенту.

### 8.3 Флаги сообщений

- `duplicate_of_prev` — текст и роль совпадают с предыдущим сообщением. Не удаляй.
- `after_end` — после события завершения.
- `pii_masked` — есть маски вида «[Имя скрыто]», «[Персональные данные скрыты]». Это не ошибка оператора.
- `unknown_event` — нераспознанная системная фраза.

Сохраняй оригинал при выявлении дублей или артефактов транскрипции. Звонки содержат ошибки распознавания речи — оценивай смысл, а не опечатки. Не делай выводов о дикции и интонации только по тексту.

### 8.4 Аудио

Для аудио возвращай ссылку и временные метки. `audio_url` — тоже подписанная ссылка: не пиши её в документацию, примеры и логи. Точное смещение в записи выдавай только при подтверждённом соответствии: `audio_offset_reliable = false`, если в разговоре есть `recording_paused` или не разобрались метки.

## 9. Апелляции и история

Апелляция относится к определённой оценке и критерию (или флагу) и содержит комментарий.

Проверяющий может:
- подтвердить исходную оценку;
- изменить ответ, включая разрешённый переход N/A ↔ применимый ответ.

Причина решения обязательна. Новое значение проверяется по версии чек-листа, использованной при оценке.

Финальный результат вычисляется из исходного результата и принятых решений; исходный результат никогда не изменяется. Пересчитывай итог, секции и отдельные флаги. Сохраняй исходный результат, апелляцию, решение, причину и финальный результат.

Защита от повторного применения и конфликтов — простая: проверка статуса апелляции внутри транзакции, повторное решение → 409. Одна открытая апелляция на критерий в оценке.

Авторизация для демонстрации не требуется. Подача апелляции и её рассмотрение остаются отдельными API-действиями.

## 10. API для фронтенда

Предусмотри документированные операции:
- проверка состояния сервиса (включая провайдер модели и активную версию чек-листа);
- импорт набора по `group_id`;
- загрузка JSON;
- список разговоров с фильтрами и пагинацией;
- карточка разговора с сообщениями, фазами и флагами;
- создание и просмотр чек-листов;
- создание новой версии чек-листа и проверка без сохранения;
- активация версии чек-листа;
- запуск оценки одного или нескольких разговоров;
- получение статуса обработки;
- получение исходной и финальной оценки;
- сравнение оценок одного разговора по двум версиям чек-листа;
- подача и список апелляций;
- решение по апелляции;
- история изменений.

Все маршруты под `/api`. Ответы и ошибки имеют стабильную структуру. CORS — из конфига. Если папка `frontend/` существует, раздавай её как статику с корня `/` (только чтение), чтобы всё запускалось одной командой.

После перезапуска незавершённые задания помечаются `failed` с причиной «прервано перезапуском», готовые результаты сохраняются. Не добавляй тяжёлую инфраструктуру (очереди, Redis, Docker) без необходимости.

## 11. Проверки

Напиши и выполни тесты для критической логики:

- все применимые оценки максимальны → 100;
- критерий 6 со значением 7 при весе 15 → 10,5 до нормализации;
- критерии 2 и 3 = N/A; значения остальных: Да, 15, Да, 7, Нет → 77,69;
- в предыдущем примере апелляция меняет завершение с Нет на Да → 85,38;
- только критерий 3 = N/A; значения: Да, Да, 15, Нет, 7, Нет → 63,125 → **63,13** (проверка `ROUND_HALF_UP`, не банковского округления);
- изменение N/A пересчитывает знаменатель;
- отсутствие применимых весов в пользовательском чек-листе → null;
- грубое нарушение не обнуляет итог;
- запрещённый N/A и неверная ступень шкалы отклоняются;
- неизвестные, пропущенные и повторные ID критериев отклоняются;
- доказательство с несуществующим ID отклоняется;
- новый критерий с новым ID работает без изменения кода;
- замена одного критерия вызывает модель только для него; изменение только веса не вызывает модель (счётчик вызовов FakeLLM);
- старая оценка сохраняет прежнюю версию правил;
- апелляция не уничтожает исходный результат;
- повторный импорт и повторное решение не создают дубликаты;
- RU/KZ/EN и оба формата времени обрабатываются;
- все 26 системных фраз из раздела 8.1 дают свои коды; новая фраза → `unknown`;
- фазы на синтетической фикстуре удержания совпадают с таблицей из 8.2;
- импорт с неизвестной ролью, без `audio_url` и с одной битой записью проходит, остальные записи сохранены;
- дубли помечаются, но не удаляются;
- ошибка модели не выдаётся за успешную оценку;
- история сохраняется после перезапуска;
- инструкции внутри транскрипта не меняют правила оценки.

В DEV нет готовой официальной разметки. Не объявляй тесты схем и арифметики доказательством точности ИИ. Семантические тестовые ответы помечай как вручную подготовленные ожидания.

## 12. Репетиция контрольного набора

На 23-м часу будет один час на неизвестный набор. Подготовь скрипты (Python, запуск из `backend/`):

- `scripts/data_report.py --group <ID>` или `--file <path>` — отчёт по набору, главное — нераспознанные системные фразы и неизвестные роли/каналы/языки.

Цель: весь DEV (65 разговоров) на настоящей модели оценивается за несколько минут. Фактическое время запиши в `docs/DATA_NOTES.md`.
