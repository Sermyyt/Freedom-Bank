# Заметки фронтенда CQA

Рабочие заметки Claude Code по `frontend/`: запуск, наблюдения об API, принятые решения, что проверено.
Правила — `CLAUDE.md`, ТЗ — `docs/FRONTEND_SPEC.md`, источник истины об API — `docs/examples/*.json`, затем `docs/openapi.json` и `docs/API_CONTRACT.md`.

## Запуск (Windows PowerShell, из корня репозитория)

Папка `frontend/` должна существовать до старта сервера: FastAPI монтирует её на `/` только при запуске.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
Set-Location backend
$env:LLM_PROVIDER = 'fake'
..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Интерфейс: `http://127.0.0.1:8000/`. Проверка сервера: `http://127.0.0.1:8000/api/health`, Swagger: `http://127.0.0.1:8000/docs`.
База — `data/cqa.db` (в `.gitignore`). Чтобы начать с чистого состояния, остановите сервер и удалите `data/cqa.db`.

Тесты фронтенда (нужен Node.js 18+, без npm-зависимостей):

```powershell
node --test frontend/tests/
```

### Python 3.14 на этом ПК

На машине установлен только Python 3.14. Для него нет готовой сборки `pydantic-core==2.33.1`, которую требует закреплённый `pydantic==2.11.3`, поэтому `pip install -r backend\requirements.txt` падает. Python 3.13 из `uv` блокируется политикой Windows (Smart App Control).
Локально `.venv` собрана так (файлы бэкенда не менялись):

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --only-binary=:all: fastapi==0.115.12 "pydantic>=2.12,<2.13" uvicorn==0.34.2 pytest==8.3.5 httpx==0.28.1 python-multipart==0.0.20 python-dotenv==1.1.0
```

С этим окружением тесты бэкенда (`python -m pytest` из `backend/`) прошли: 282 passed, 2 skipped. Отличие от закреплённых версий — только pydantic 2.12.5. Если есть Python 3.11–3.13, используйте обычную команду из README.

## Наблюдения об API (сверено с примерами и кодом)

- Все ответы в конверте `{data, meta.request_id}`, ошибки — `{error: {code, message, details, retryable}, meta}`. `message` уже безопасный русский текст.
- Строгие query-параметры: неизвестный или повторённый параметр → 422 `VALIDATION_ERROR`. Пустые фильтры не отправляем совсем (иначе `language=` станет фильтром по пустой строке).
- 429 `BUSY` приходит с заголовком `Retry-After: 1`.
- Значения из данных: `channel` — `agent chat`, `voice call`; `language` — `RU`, `KZ`, `EN`; `speaker` — `client`, `operator`, `bot`, `system`. Неизвестные значения сервер сохраняет как есть — интерфейс показывает их как есть.
- `audio_offset_sec` сейчас всегда `null`, а `audio_offset_reliable` всегда `false` (так заполняет `backend/app/ingestion.py`). Значит, кнопок перехода по времени записи в текущей версии не будет, а у звонков с аудио всегда будет подпись «Точное время в записи не гарантировано». Это честное поведение по контракту.
- `phase` и `client_facing` уже вычислены сервером: `client_facing = phase ∈ {pre_operator, client}`. Фронт не определяет фазы сам, только группирует подряд идущие `hold`/`internal_consult` в блоки.
- В `sections` нет секции, где только флаги (в seed — «Грубые нарушения»): у неё нет веса. Флаги показываем отдельным блоком по `final.flags`.
- `contribution`, `effective_weight`, `completion_percent`, `contribution_delta` приходят неокруглёнными (например, `0.891089108910892`). Фронт только форматирует до `scoring_policy.decimals` знаков.
- `GET /api/evaluations` по умолчанию отсортирован `created_at DESC` — первая запись и есть последняя оценка.
- `ConversationSummary.has_open_appeals` относится к последней оценке текущей ревизии; после импорта новой ревизии `latest_evaluation = null` до новой оценки.
- `dataset_ready=false` по умолчанию (нет `DATASET_URL`): импорт по группе недоступен, работает импорт файлом.
- После phase 5 бэкенда FakeLLM отвечает разнообразно: «Нет», ступени шкалы ниже максимума, флаг «Нарушение», «Нужна ручная проверка», доказательства из неклиентских фаз. `checked_range` в синтетическом звонке не приходит. `EvaluationSummary` теперь содержит `scoring_policy` (см. `FRONTEND_REQUESTS.md`, п. 2).
- Апелляции: в `Appeal` нет разговора и названия критерия, только `evaluation_id` и `criterion_id`. В ошибке `DUPLICATE_OPEN_APPEAL` нет ID уже открытой апелляции. `GET /api/appeals` отсортирован `created_at DESC`, `limit` не больше 100.
- Кеш `frontend/`: раньше статика раздавалась без заголовков кеширования, и Chrome эвристически держал старые `js/*.js`. С phase 6 бэкенд отдаёт `Cache-Control: no-cache`, браузер перепроверяет файлы. Вкладку, открытую до обновления, один раз перезагрузите с Ctrl+Shift+R. Тестовый браузер проверок запускается с отключённым кешем.
- Сервер сначала проверяет, что апелляция открыта, и только потом `expected_final_revision`: апелляция, решённая параллельно, даёт `APPEAL_ALREADY_RESOLVED`, а не `VERSION_CONFLICT`.

### Карточка разговора (F2)

- Какая оценка и ревизия показаны: `?evaluation=` — эта оценка и её ревизия; `?revision=` — последняя оценка этой ревизии (или никакой); без параметров — последняя оценка разговора и её ревизия. Если это не текущая ревизия, сверху пояснение и ссылка «Открыть текущую ревизию». Доказательства всегда раскрываются в ревизии оценки.
- «Оценить» отправляет `{"revision_ids": [<текущая ревизия>]}`. Если показана старая ревизия, кнопка называется «Оценить текущую ревизию». POST не повторяется; задание опрашивается раз в секунду, при уходе с экрана опрос останавливается.
- Если `?evaluation=` не найдена или относится к другому разговору, показывается сообщение и последняя оценка разговора.
- «Сравнить с текущей» есть только у оценок той же ревизии: сервер сравнивает только такие (иначе 409 `INCOMPARABLE_EVALUATIONS`).
- Флаги идут отдельным блоком под критериями. Грубое нарушение — отдельная красная плашка, балл она не меняет; меняет его только `total`, который пришёл с сервера.
- Полоса под итогом показывает `contribution` секций на шкале 0–100. Остаток штрихуется: это недобранные баллы. Таблица секций подписывает «Выполнение секции» (`completion_percent`) и «Вклад в итог» (`contribution`) раздельно.

### Апелляции (F3)

- **Подача.** У каждого критерия и флага есть кнопка «Оспорить». Она открывает модальное окно (`<dialog>` внутри `#cqa-root`) с текущим ответом, обоснованием и полем «Комментарий оператора». Тело запроса — ровно `{evaluation_id, criterion_id, comment}`, комментарий без пробелов по краям.
- **Дубль.** На 409 `DUPLICATE_OPEN_APPEAL` показываем «По этому критерию уже есть открытая апелляция» и ссылку на неё. ID открытой апелляции берём из `GET /api/appeals?evaluation_id=…&status=open`, потому что в ошибке его нет.
- **Где решают.** Решение принимается в карточке разговора, в панели под критерием, а не в модальном окне. Пока выбрано «Изменить ответ», по репликам переписки слева можно щёлкать: реплика добавляется в доказательства, повторный щелчок её убирает. С клавиатуры то же делают Tab и Enter или пробел. Выбранные реплики отмечены маркером, как доказательства в оценке.
- **Решение из списка.** В `#/appeals` кнопка «Рассмотреть» открывает `#/conversation/<id>?evaluation=<оценка>&appeal=<апелляция>` с уже открытой панелью и ссылкой «К апелляциям». Подача и решение — два отдельных действия.
- **Перед решением.** Панель заново загружает оценку. Из неё берутся `final_revision` (уходит как `expected_final_revision`) и текущий ответ критерия: он показан как «Сейчас засчитано» и отмечен «сейчас» среди вариантов.
- **Варианты нового ответа.** Это опции критерия из `checklist_snapshot` этой оценки с теми же подписями, что в карточке. N/A предлагается только при `na_allowed` и требует причины.
- **Тело запроса.** «Подтвердить» отправляет только `action`, `reason` и `expected_final_revision`. «Изменить» добавляет `new_answer`, для N/A ещё `na_reason`, а `evidence_message_ids` — только если реплики выбраны. Без доказательств сервер добавляет предупреждение, и форма заранее об этом говорит. `rationale` не отправляем: сервер берёт обоснование из `reason`.
- **Пересчёт.** После решения у критерия появляется «Решение сохранено, итог пересчитан»: «ответ было → стало» и «итог до → после». «До» — финальный итог перед решением, «после» — итог из ответа сервера. Затем карточка перезагружается. Решённые апелляции остаются у критерия в истории: дата, решение, комментарий оператора, причина проверяющего.
- **Конфликты.** На 409 `VERSION_CONFLICT` показываем «Оценка изменилась, данные обновлены», заново загружаем оценку, а введённое в форме сохраняется. На 409 `APPEAL_ALREADY_RESOLVED` — сообщение, панель закрывается, карточка обновляется.
- **Список `#/appeals`.** Фильтр «Открытые» (по умолчанию), «Решённые», «Все» хранится в адресе, 25 строк на страницу. Колонки: разговор, критерий, комментарий, дата подачи, статус, решение (было → стало, причина, дата). Разговор и название критерия берутся из оценки: одна загрузка `GET /api/evaluations/{id}` на оценку страницы (см. `FRONTEND_REQUESTS.md`, п. 3).

### Чек-лист и сравнение (F4)

- **Что загружается.** Редактор открывает активную версию: `active_checklist_version_id` из свежего health, затем `GET /api/checklist-versions/{id}`. Версии берутся без кеша, потому что `is_active` вычисляет сервер. Справа список версий (`GET /api/checklists/{id}/versions`) с отметками «активна» и «в редакторе».
- **Критерии.** Разлинованный список в порядке версии. Строка раскрывается в форму:
  - ID: у существующих только для чтения, у нового — ввод латиницей с подсказкой;
  - название, секция (с подсказками уже встреченных секций), тип ответа, вес (скрыт у флага), описание;
  - «Разрешить N/A» и условие N/A;
  - варианты ответа: у `binary` и `flag` ровно true/false с подписью и описанием; у `scale` ступени со значением, подписью, описанием и долей балла (пусто — сервер подставит «значение / максимум», подсказка показывает это число).
- **Действия у критерия.** «↑» и «↓» сохраняют фокус на стрелке. «Удалить» показывает уведомление с «Вернуть». «Добавить критерий» есть над списком.
- **«Заменить».** Ставит в тот же слот новое правило: поля копируются для правки, ID предлагается `<старый>_v2` (занятые пропускаются, `_v2` → `_v3`), фокус в поле ID, метка «заменяет contact», есть «Отменить замену». Так сравнение честно покажет старое правило «Удалён», а новое «Добавлен», как требует контракт: у принципиально другого правила новый ID.
- **Проверка на клиенте.** Сервер не проверяет только одно: ID нового правила должен быть латиницей и не совпадать с ID правила прежней версии. Это проверяется в форме.
- **Живая проверка.** Через 500 мс после правки отправляется `POST /api/checklists/validate`; устаревшие запросы отменяются. Ошибки показываются у полей по `details.path` (`criteria.0.weight` и т. п.), а у свёрнутого критерия в строке появляется метка «есть ошибки». Ошибки без поля выводятся отдельным списком, предупреждения — отдельно. После перемещения, удаления или смены типа проверка запускается сразу, потому что индексы в путях меняются.
- **Панель сохранения.** Закреплена внизу экрана (на телефоне — обычный блок). На ней статус проверки, сводка изменений («заменено правил: 1, изменён порядок…»), галочка «Сразу применить» (включена по умолчанию), «Отменить изменения» и «Сохранить новую версию». Без изменений или с ошибками сохранение недоступно.
- **Сохранение.** `POST /api/checklists/{id}/versions`: определение, `expected_latest_version_id` и `activate`. При активации добавляется `expected_active_version_id` из свежего health, в том числе `null`. После сохранения обновляются шапка («Чек-лист v2»), редактор и список версий. 409 `VERSION_CONFLICT` даёт «Чек-лист изменился, загружена последняя версия» и загрузку последней версии.
- **После сохранения с активацией** появляются «Переоценить разговор» и «Сравнить с прошлой оценкой»:
  - разговор — последний открытый в карточке, его внешний ID виден;
  - переоценка отправляет `{"revision_ids": [текущая ревизия], "checklist_version_id": <новая версия>}` и показывает ход задания;
  - сравнение становится доступно после переоценки и открывает `#/compare` с прошлой оценкой той же ревизии слева и новой справа;
  - если разговор ещё не открывали, вместо кнопок подсказка со ссылкой на список. Без активации кнопок нет, и сказано, что версия не применена.
- **Сравнение `#/compare`.**
  - Сверху итог слева и справа (версия чек-листа, дата, статус, «исходно … после апелляций», если отличается) и разница итога со знаком.
  - Таблица идёт в порядке сервера: критерий и ID, изменение правила (метка и цветная полоса строки; у `weight_changed` ещё «вес 10 → 15»), ответ слева и справа по своему снимку (изменившийся ответ подсвечен), разница вклада.
  - Разница показана знаком «+»/«−» и цветом вместе; `null` — «—» с подсказкой, а не 0. В заголовках колонок — версии («Слева, Чек-лист v1»).
  - Без параметров — пустое состояние с подсказкой; разные ревизии — сообщение сервера и пояснение.

### Оценка всей группы (F5)

- **Где.** Блок «Оценить всю группу» стоит в списке разговоров, между фильтрами и таблицей.
- **Какая группа.** Группа берётся из применённого фильтра «Группа». После импорта список сам фильтруется по импортированной группе, поэтому сценарий 23-го часа такой: импорт → «Оценить всю группу». Без выбранной группы кнопка недоступна, рядом подсказка.
- **Запрос.** Ровно `{"group_id": "…"}`, без `revision_ids`. Сервер оценивает текущие ревизии всех разговоров группы по активному чек-листу независимо от остальных фильтров, и подсказка об этом говорит. POST не повторяется.
- **Ход задания.** Тот же компонент, что в карточке: статус, полоса, «обработано / успешно / с ошибкой / на ручную проверку». Ошибки элементов подписаны внешним ID разговора, если строка уже была в таблице, и прокручиваются внутри блока.
- **По окончании.** Таблица перезагружается, появляется уведомление с итогом («Группа X оценена: успешно N из M…» или «…с ошибками»), а кнопка «Скрыть итог» убирает ход задания. Группа без разговоров (404) даёт сообщение сервера у блока.
- **Уход со списка.** Задание хранится в памяти вкладки (не в `localStorage`). Если открыть разговор и вернуться к списку, опрос продолжится, а по окончании таблица обновится. Если опрос сорвался, задание на сервере продолжается: вместо второго запуска показывается «Проверить снова».

### История (F5)

- **Данные.** `GET /api/history`, сначала новые, 25/50/100 на страницу. Фильтры в адресе: `#/history?event_type=…&conversation_id=…&offset=…`; мусор из адреса отбрасывается.
- **Строка.** Время, событие человеческими словами (неизвестный тип — как есть), `summary` сервера, связанные объекты и автор («Система», «Оператор (демо)», «Проверяющий (демо)» — `demo_*` не выдаём за подтверждённых людей).
- **Ссылки.**
  - «Разговор <внешний ID>» ведёт в карточку.
  - «Оценка» — в карточку с этой оценкой.
  - «Апелляция» — в карточку с `?appeal=`: открытая откроет панель решения, у решённой будет сообщение, что решение показано у критерия.
  - У событий чек-листа — «Чек-лист vN» на редактор. У оценки — «по чек-листу vN» текстом.
- **Фильтр по разговору.** В истории только внутренний ID, поэтому разговор ищется по внешнему ID через `GET /api/conversations?q=…`. Точное совпадение применяется сразу, несколько — список для выбора, ничего — ошибка у поля. Активный фильтр виден плашкой «Только события разговора X» с «Показать все разговоры».
- **Внешний ID в строках.** Берётся из `GET /api/conversations/{id}`, по одной загрузке на разговор; детали разговора в браузере нигде не сохраняются.
