# AGENTS.md — постоянные правила для Codex в этом репозитории

Проект: CQA (Conversation Quality Analytics) — кейс Freedom Broker на хакатоне.
Бэкенд (`backend/`) — твоя зона. Фронтенд (`frontend/`) пишет человек.
Полное ТЗ: `docs/BACKEND_SPEC.md`. Эти правила действуют в КАЖДОЙ сессии, даже если в задаче о них не сказано.

## 1. Границы

- Не создавай, не изменяй, не удаляй и не форматируй файлы в `frontend/`. Если фронту нужно что-то новое — опиши это в `docs/API_CONTRACT.md`.
- Не читай и не выводи значения из `.env` в код, тесты, логи, коммиты, документацию. Используй только имена переменных.
- Никогда не коммить: `.env`, `data/`, `*.db`, `docs/source/` (PDF организаторов), любые ссылки с параметром `sig=`.
- Не удаляй и не переписывай целиком работающие модули. Меняй точечно и только то, что нужно для текущей задачи.

## 2. Источники истины (по убыванию)

1. Гайд и чек-лист организаторов в `docs/source/` (PDF) — правила оценки и требования.
2. Фактические данные из API организаторов — структура данных.
3. `docs/BACKEND_SPEC.md` — ТЗ, написанное до детального изучения PDF. **В нём могут быть ошибки.** Пункты с пометкой [ПРОВЕРИТЬ] — предположения.

Если ТЗ противоречит пунктам 1 или 2 — следуй 1/2 и запиши в `docs/DECISIONS.md`: что сказано в ТЗ, что на самом деле, что ты выбрал и почему.

## 3. API-контракт с фронтом

- Контракт = `docs/API_CONTRACT.md` + OpenAPI + Pydantic-схемы в `backend/app/schemas.py`. Человек пишет фронт строго по ним.
- Разрешены только **добавления**: новые поля, новые эндпоинты, новые значения enum в конце списка.
- Запрещено без явного согласия человека: переименовывать или удалять поля и эндпоинты, менять тип поля, менять смысл значения. Если без этого никак — запиши предложение в раздел «Изменения» в `docs/API_CONTRACT.md` с пометкой BREAKING и **остановись, спроси**.
- `docs/examples/*.json` генерируются скриптом `backend/scripts/gen_api_examples.py` из реальных ответов API (на FakeLLM), а не пишутся руками. После изменения API — перегенерируй.

## 4. Правила кода

- Арифметику баллов делает только `backend/app/scoring.py`. Модель баллы не считает и не округляет.
- Никаких захардкоженных id или названий критериев в логике (scoring, evaluator, validation, prompt). Критерии существуют только как данные: seed JSON и БД. Проверка: `grep` по id критериев в `backend/app/` должен находить их только в seed-файле.
- Правила оценки, по которым ещё нет ответа менторов (округление, обнуление при грубой ошибке и т. п.), — только через конфиг, не константами в коде.
- Исходные реплики разговора не изменяй: не удаляй дубли, не «чисти» текст. ID сообщений должны оставаться стабильными.
- Кроссплатформенность (человек на Windows): `pathlib`, только Python-скрипты (никаких bash), файлы читать и писать в UTF-8, `json.dumps(..., ensure_ascii=False)`.
- Зависимости — только необходимые, версии зафиксированы в `backend/requirements.txt`.

## 5. Тесты и фазы

- Работай фазами из ТЗ. Фаза закончена, когда `python -m pytest` (из `backend/`) зелёный и сделан коммит.
- Не начинай следующую фазу при красных тестах.
- Не правь и не удаляй существующие тесты ради того, чтобы они прошли. Если тест противоречит гайду — исправь его и объясни в `docs/DECISIONS.md`.
- Тесты не ходят в сеть и не вызывают настоящую модель: только `FakeLLM` и фикстуры. Тесты на реальных данных DEV помечай `skipif`, если файла `data/raw/DEV.json` нет.

## 6. Если что-то неясно

- Не блокирует работу → выбери самый простой обратимый вариант, запиши в `docs/DECISIONS.md`, продолжай.
- Блокирует или ломает контракт / удаляет данные / необратимо → остановись и спроси.

## 7. Перед каждым коммитом

- [ ] `git status`: нет `.env`, `data/`, `*.db`, PDF, ссылок с `sig=`
- [ ] если менялся API — обновлены `docs/API_CONTRACT.md` и перегенерированы `docs/examples/`
- [ ] если принято решение вопреки ТЗ — есть запись в `docs/DECISIONS.md`
- [ ] сообщение коммита: `phase N: что сделано`
